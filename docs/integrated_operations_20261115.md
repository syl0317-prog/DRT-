| 기존 업무군 | 문제 | 변경 결과 |

| 정시·환승 분석 | 고정 운영과 별도 최근접 12개 역 분석 | 기본 8개 정류장 고정 목적지 분석, 기존 최근접 비교는 연구 옵션 |

새 메뉴는 **통합 대시보드 / 예약 및 배차 관리 / 노선 및 운영 관리 / 시뮬레이션 및 정시성 분석 / 데이터 및 시스템 관리** 5개다.
예약·목록·취소와 지도는 좌우 컬럼에 배치했다. 기존 예약 입력 화면의 중복 진입은 통합 입력으로 대체하고, 기존 CSV 예약은 그대로 조회·취소 오버레이 및 픽업/합승 계산에 사용한다. 기존 연구 알고리즘 모듈은 삭제하지 않았다.

## 2. 노선 및 실제 정류장 소속

| 노선 | 가상정류장 | 소속 근거 | 고정 목적지 |
|---|---|---|---|
| R01 | D01, D02, D03, D04 | sewook31/data/drt_stops.csv 및 기존 통합 코드의 legacy=R01 식별 규칙 | T01 위례별역 |
| R02 | V05, V06, V07, V08 | data/derived/drt_routes/routes.sqlite3 등록부의 route_id·stop_order; data/seeds/drt_routes.json 복구 자료와 일치 | T02 위례역사공원역 |

CSV에는 R01 열 자체가 없으며 기존 코드의 R01 식별 규칙을 계승했다. R02 소속은 저장된 등록부에서 확인했다. T01/T02 고정 목적지는 이번 사용자 운영 지시로 적용한 정책이다. 기존 R02 등록부의 transfer_stop_id는 null이며 이를 몰래 T02로 수정하지 않았다. 중복 소속·미소속은 예외로 중단한다.

## 3. R02 예약 실패 원인 및 수정

- 원본 R02 방문 순서는 V05→V06→V07→V08, 트램 연결 ID는 null이다. 기존 `_ordered_route`는 T02를 방문 순서에서 찾지 못해 R02 선택 시 거절했다.
- 이제 승차 소속과 고정 목적지를 먼저 검증한다. R02→T02는 유효한 요청으로 SQLite에 저장하며 `route_id=R02`를 유지한다.
- 활성 상태, 전체 도로 구간 및 차량 조건이 충족되지 않으면 **배차 검토 필요**, 차량 null로 유지한다. 실제 운행 확정이라고 표시하지 않는다.
- 운영 관리에서 T02 연결, 방문 순서·전용 차량 설정, 전체 구간 계산, 활성화 후 동일 접수를 재검토할 수 있다. 배차는 정원·시간 중복·날짜 불명 기존 CSV 차량 점유·가상 트램 목표 시각을 확인한다.
- 동일 요청 키는 SQLite UNIQUE 및 트랜잭션으로 재사용한다. UI 기본 키는 입력 서명으로 만들어 새 세션 새로고침에도 중복을 막는다. 별도 추가 요청은 명시적 버튼으로 새 키를 만든다.
- CSV는 가져와 재저장하지 않는다. CSV 취소는 별도 취소 테이블이며 기존 좌석 계산 읽기에도 반영한다. 날짜가 없는 과거 CSV를 새 날짜 기반 요청과 자동 합치지 않는다.
- 원본 과거 예약 중 고정 목적지 정책과 다른 조합은 자동 변경하지 않고 시스템 화면에서 경고한다.

## 4. 지도 복원 및 통일

R01 캐시는 `lat,lon` 소수 6자리 키였고 현 조회 함수는 `driving|lon,lat` 소수 7자리만 조회했다. 기존 방향별 키를 읽도록 호환 처리했다. 지도는 위도·경도 순서로 렌더링한다.

- R01: D01~D04 각각 T01로 향하는 저장 OSRM 도로 모형 4개를 파랑 `#2563EB` 실선으로 표시한다. 이는 정류장별 경로 모음이며, 임의로 확정한 전체 순환 순서·총거리가 아니다.
- R02: 등록부에 저장된 V05→V06→V07→V08의 3개 도로 구간은 주황 `#F97316` 실선으로 표시한다.
- V08→T02는 현재 도로 구간 자료가 없어 주황 점선 **추정 연결선**으로 표시하며, 전체 거리·시간은 산출하지 않는다.
- 가상정류장 8개는 노선색 원형 마커, 트램 2개는 열차 아이콘이다. 정보 팝업과 노선별 숨김 레이어를 제공한다.
- 대시보드·예약 옆 지도·통합 노선 지도·R02 관리 지도는 공통 `route_layers/add_layers`를 사용한다. 임의 경유지 연구 도구와 동적 관제 모형은 운영 경로와 별도 연구 기능이다.
- 지도 조회는 오프라인 캐시 우선이며 자동 외부 API 호출을 하지 않는다. 명시적 온라인 조회 결과로도 기존 OSRM 캐시를 덮어쓰지 않는다.

## 6. 검증

자동화는 원본 예약 CSV 복사본·SQLite backup 복사본과 임시 DB를 사용한다. 시험용 마지막 R02 구간과 차량은 임시 DB에만 생성한다.

- 8개 소속 및 미소속·중복 소속 검사, 잘못된 목적지/노선 조합 거절.
- R01→T01, R02→T02 생성·재조회·취소·원본 보존, 동시 4개 동일 요청 중복 방지.
- 비활성 R02 미확정 처리, T02 미연결 활성화 방지, 정원·시간 충돌, 취소 후 좌석 회수·대기 접수 재검토.
- R01 저장 경로 4개·R02 저장 구간 3개·추정 연결 1개, 좌표 범위, 8개 원형 마커·2개 트램 아이콘 및 공통 색상.
- Streamlit AppTest: 5개 메뉴와 하위 분석·운영 화면, 정류장 선택 후 자동 목적지, 실제 예약 버튼·취소 버튼.
- 기존 정시성 수학 검증과 최초 초기화 보존 회귀 포함.
- Windows Python 3.12, Streamlit 서버 127.0.0.1:8517 시작 및 `/_stcore/health = ok` 확인.
- 실제 브라우저 시각 검증은 computer-use 도구가 현재 URL을 확인하지 못해 중단됐다. 지도 타일·아이콘·폭·스크롤의 사람 확인이 필요하다.

최종 결과: 메인 앱 회귀 14개 전부 통과(154.360초). 기존 데이터 85개 SHA256 비교에서 변경·삭제 0개. `git diff --check` 통과. 테스트용 8517 서버는 헬스 체크 후 종료했다. 기존 사용자 서버는 종료하지 않았다. 별도 `drt_system` 앱 테스트 전체 실행이나 실제 브라우저 시각 검증까지 통과했다고 주장하지 않는다.

## 8. 남은 한계와 실제 웹 확인 절차

1. R02의 V08→T02 방향 도로 경로 및 통행 적합성을 검증하고, 운영자가 전용 차량을 지정한 뒤 전체 구간을 계산·활성화해야 한다. 이번 작업에서 실제 등록부·예약은 임의 변경하지 않았다.
2. R01 날짜 기반 접수는 배차 검토 상태다. 실제 운영 차량·운영일·서비스 시간·차량 현위치 자료 없이 과거 날짜 불명 CSV 차량을 가용 차량으로 확정할 수 없다.
3. 실측 평균 대기시간·정시율·운행 중 차량 수는 관측 이벤트가 없어 산출 불가다. 운영 이벤트와 차량 위치 수집이 향후 필요하다.
4. GITS/TOPIS 관측시각·방향별 도로 매칭을 검증해야 실시간/시간대별 배차 예측에 연결할 수 있다. 현재 과거 연구 결과를 실시간으로 표시하지 않는다.
5. 연구용 차량 슬라이더·실행 결과는 세션 설정이다. 예약과 취소는 SQLite로 보존되지만 분석 세션 상태까지 영구 저장한다고 보장하지 않는다.
6. 실제 브라우저에서 R01 파랑 실선, R02 주황 및 마지막 점선, 8개 정류장·2개 트램, 레이어 토글을 확인한다. 원본 데이터 보호를 위해 실제 예약 생성·취소 실습은 별도 복사 환경을 사용한다.
